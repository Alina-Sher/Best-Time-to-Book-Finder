# Travel.pk — Best Time to Book Finder

A Streamlit analytics app for **Travel.pk** (TechAbout's online travel agency for Pakistan). For a chosen
flight route and travel month it answers:

> *How far in advance should I book, based on the available fare data?*

> ## ⚠️ Data status: DEMO / SIMULATED
> No legitimate, accessible historical fare dataset for Pakistan domestic routes could be found (see
> [Data source investigation](#data-source-investigation)). The app therefore ships with a **clearly labelled
> simulated dataset**. Its fares are random numbers generated from assumptions in
> `data/generate_demo_data.py`. **They are not real airline fares**, and the booking-window "patterns" show
> the *method*, not real-world behaviour. The dataset can be replaced with a real one without code changes
> (see [Replacing the demo data](#replacing-the-demo-data)).

## Assigned task

**Best Time to Book Finder** — "Analyze fare data to show when travelers should book for a given route and
month. Submit live URL."

## Main features

- Select origin, destination, travel month and year → **Find Best Time to Book**.
- Booking windows: 0–3, 4–7, 8–14, 15–30, 31–60, 61–90 days before departure (configurable).
- Per window: itinerary count, raw snapshot count, median, mean, standard deviation, 25th–75th percentile range.
- Recommendation = eligible window with the lowest median, with a rule-based **Strong / Moderate / Limited**
  evidence label (not a probability) and a "not a guarantee" caveat.
- Explicit **"Not enough data for a reliable recommendation"** state (minimum sample sizes are configurable).
- Charts: median-fare line chart (with IQR band), median bar chart, sample-size chart — all built from the
  same table that is displayed.
- States: initial, loading, results, insufficient data, invalid route, route not in dataset, no data for the
  month, data-loading/processing error, demo-data disclosure.
- Built-in **Data sources and methodology** section (dataset facts, field definitions, calculation steps,
  cleaning rules with live exclusion counts, limitations).

## Technology stack

Python 3.10+ · Streamlit · pandas · NumPy · Plotly. Tests use `unittest` (also runnable with `pytest`).

## Data source investigation

Findings from the development session (20 Oct 2026):

- **Open data:** web searches for a public historical-fare dataset covering Lahore/Karachi/Islamabad routes
  returned nothing usable. No dataset with fare *observation date* + *departure date* for Pakistan was found.
- **Commercial providers** (e.g. OAG airfare data, data marketplaces) are paid products — excluded by the brief's
  "no undisclosed paid subscription" rule.
- **Scraper services** for flight sites were not used: they are paid and scraping third-party sites risks
  violating their terms.
- **Kaggle / GitHub raw files:** the development sandbox's network policy blocked these hosts, so they could
  **not** be inspected. This means the existence of a suitable public dataset on those platforms is
  *unverified*, not ruled out. Even a good non-Pakistani dataset would not support the Pakistan routes.
- **APIs:** none was used or tested. Flight-search APIs generally return current offers, not price histories,
  so they cannot support this analysis without accumulating your own snapshots over time.

**Decision:** simulated demo data, labelled everywhere it is used (banner, result card, methodology).

## Data and methodology (summary — the app shows the full version)

| Item | Value |
|---|---|
| Dataset | Travel.pk Best-Time-to-Book DEMO dataset (SIMULATED) |
| Real or simulated | **Simulated** |
| Source URL | None — generated by `data/generate_demo_data.py` (seed 20250101) |
| Generation date | See `data/demo_fares.metadata.json` |
| Coverage | One-way, LHE↔KHI, LHE↔ISB, KHI↔ISB (6 directional routes), departures Jan–Dec 2025 |
| Observation period | Oct 2024 – Dec 2025 (each itinerary has 10 snapshots, 0–90 days before departure) |
| Currency | PKR, whole rupees |
| Deliberate gaps | ISB→KHI Feb 2025 is thin (→ insufficient data); KHI→ISB Jan 2025 has no departures (→ no data) |

### Booking-window calculation

1. Filter to origin, destination and departure month/year.
2. `lead_days = departure_date − observation_date` (whole days).
3. Assign each observation to a window; observations beyond 90 days are counted but not analysed.
4. **Collapse repeated snapshots:** snapshots of the same itinerary (route + carrier + departure date) inside one
   window are reduced to their median. The unit of analysis is *itinerary-in-window*, so sample sizes count
   distinct itineraries, not rows.
5. Per window: n, median, mean, standard deviation, 25th/75th percentile; for eligible windows a 95 % bootstrap
   interval of the median (1,000 resamples, fixed seed, so results are deterministic).
6. Eligibility: ≥ **30** itineraries per window (`min_samples_per_window`) and ≥ **3** eligible windows
   (`min_eligible_windows`), otherwise "Not enough data for a reliable recommendation".
7. Recommended window = eligible window with the lowest median (ties → longer lead time).
8. Comparison window = the eligible window closest to departure ("last-minute baseline"). Differences are shown
   only against it, and no saving is claimed if the baseline is itself the cheapest.
9. Evidence label: one point if the recommended window has ≥ 100 itineraries, one if its bootstrap interval does
   not overlap the next-cheapest window's. 2 = Strong, 1 = Moderate, 0 = Limited.
10. No look-ahead: each fare is the price seen on its own observation date and is never used as information
    available earlier.

All thresholds live in `besttime/config.py`.

### Cleaning rules

Rows are excluded, never silently repaired, and counted in the app: missing route, origin = destination,
missing/non-ISO dates, observation after departure, missing currency, currency other than the dataset's
(no conversion), invalid fare (missing, non-numeric, ≤ 0, or > 2,000,000), duplicates (same `obs_id`, or same
itinerary + observation day + fare). Missing carrier becomes `UNKNOWN`.

### Limitations

- Demo data only demonstrates the method; it cannot show real booking behaviour.
- Historical association, not a forecast. Past patterns may not repeat.
- Nearby dates and carriers share demand conditions, so the effective sample is smaller than the itinerary count;
  the bootstrap treats itineraries as independent.
- Windows may contain different itineraries, so differences can reflect which flights were observed and not only
  when they were booked. (The demo data observes every itinerary in every window; real data usually does not.)
- No claim is made about best day of week, a universal booking rule, or future prices.
- Fares are observations, not bookable offers.

## Replacing the demo data

1. Put your CSV in `data/` (e.g. `data/real_fares.csv`) with columns
   **`obs_id, origin, destination, observation_date, departure_date, fare, currency`**
   (optional: `carrier, trip_type, itinerary_id, source`). Dates must be ISO-8601 (`2025-03-15`); fares plain numbers.
   `observation_date` must be the date the fare was **seen/quoted** (not a monthly average).
2. Create `data/real_fares.metadata.json` with at least `name`, `is_synthetic` (`false`), `currency`, and ideally
   `source_url`, `retrieved_date`, `geographic_coverage`, `observation_semantics`, `field_definitions`,
   `provenance`, `limitations`, `license` (copy `demo_fares.metadata.json` as a template).
3. Point the app at it: set the environment variable `TRAVELPK_FARE_DATA=data/real_fares.csv`
   (or change `DEFAULT_DATA_PATH` in `besttime/config.py`). On Streamlit Community Cloud add it under
   *Settings → Secrets / environment* or simply commit the new default path.
4. The demo banners disappear automatically when `is_synthetic` is `false`. The app refuses to load a dataset without a
   metadata file, so provenance can never be implied.

No credentials are required for the demo. Never commit API keys; use `.streamlit/secrets.toml` (git-ignored)
or the host's secrets manager if you later add a live data source.

## Local setup on Windows

Install [Python 3.10+](https://www.python.org/downloads/) (tick **Add Python to PATH**), then in PowerShell
or Command Prompt, inside the project folder:

```bat
python -m venv .venv
.venv\Scripts\activate
python -m pip install --upgrade pip
pip install -r requirements.txt
streamlit run app.py
```

Streamlit prints a **local** URL (normally `http://localhost:8501`). That address only works on your own computer —
it is *not* the public submission URL.

## Running tests

```bat
python -m unittest discover -s tests -t . -v
```

or, with pytest (`pip install -r requirements-dev.txt`): `python -m pytest`.

`tests/test_charts_plotly.py` is skipped automatically unless `plotly` is installed — after
`pip install -r requirements.txt` it runs and checks the real Plotly figures.

## Publishing to GitHub

1. Create a free account at <https://github.com> and install [Git for Windows](https://git-scm.com/download/win).
2. On GitHub: **New repository** → name it e.g. `travelpk-best-time-to-book` → **Public** → do *not* add a README → Create.
3. In the project folder:

```bat
git init
git add .
git commit -m "Best Time to Book Finder"
git branch -M main
git remote add origin https://github.com/<your-username>/travelpk-best-time-to-book.git
git push -u origin main
```

Check on github.com that `app.py`, `requirements.txt`, `besttime/` and `data/demo_fares.csv` are present.

## Public deployment (Streamlit Community Cloud)

1. Go to <https://share.streamlit.io> and sign in with GitHub (authorise access to the repository).
2. Click **Create app** (or *New app*) → choose the repository, branch `main`, main file path `app.py`.
3. Under *Advanced settings* pick Python 3.11 or 3.12 if offered. No secrets are needed for the demo.
4. Click **Deploy**. The first build installs `requirements.txt` and takes a few minutes.
5. When it finishes you get a public URL of the form `https://<name>.streamlit.app`. **That** is the URL to submit.

(Button labels on the hosting site may change slightly over time.)

### Testing the deployed app (manual checklist)

Open the public URL in a private/incognito window and confirm:

- [ ] The amber **DEMO / SIMULATED DATA** banner is visible at the top.
- [ ] Defaults (Lahore → Karachi, March, 2025) + **Find Best Time to Book** shows a recommendation, three charts and a table.
- [ ] Change route/month (e.g. Islamabad → Lahore, September) and search again: all numbers and charts change.
- [ ] Islamabad → Karachi, February 2025 shows **"Not enough data for a reliable recommendation"**.
- [ ] Karachi → Islamabad, January 2025 shows **"No data for this month"**.
- [ ] Lahore → Lahore shows **"Invalid route"**.
- [ ] On a phone (or a narrow browser window) controls stack vertically and charts remain readable.
- [ ] The *Data sources and methodology* section at the bottom is complete.

## Known limitations

- Simulated data only (see above); the public URL demonstrates the tool, not real fare trends.
- Only month-level departure filtering (no day-of-week analysis).
- The recommendation compares medians across windows; it does not model price paths of individual itineraries.
- Results are computed on every search from an in-memory table; very large real datasets (millions of rows)
  would call for pre-aggregation or a database.
